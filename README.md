# specIDE

Рабочая среда для требований и спецификаций. Текущий срез: создать или открыть системное требование, изменить текст и свойства, сохранить Markdown и открыть файл повторно.

## Запуск

Нужны Node.js 22.12+ и pnpm 10.13.1.

```sh
pnpm install
pnpm dev
```

Интерфейс: http://127.0.0.1:3000. NestJS API: http://127.0.0.1:4100.

По умолчанию приложение открывает `examples/workspace`. Сохранение из интерфейса меняет настоящие Markdown-файлы в этой папке. Git-версия создается только отдельным действием пользователя.

Другое рабочее пространство:

```sh
SPECIDE_WORKSPACE=/absolute/path/to/requirements pnpm dev
```

Путь должен существовать. Документы должны содержать frontmatter с `id`, `type`, `title` и `status`; пример находится в `examples/workspace/requirements/system`. В текущей версии доступны только `type: system` и ID вида `SR-001`.

Общие модели `business` и `test_case` сохранены в коде для дальнейшего развития. API исключает эти документы из списка и не принимает их сохранение; UI их не показывает. Демонстрационных BR/TC-файлов в репозитории нет, их прежние папки исключены через `.gitignore`. Существующие файлы других типов в подключенном внешнем рабочем пространстве автоматически не удаляются.

`SPECIDE_STATE_DIR` задает папку журнала операций (по умолчанию `.specide` в корне проекта). При изменении исходной папки через переменную окружения используйте отдельную папку состояния. Подключения из интерфейса получают отдельные журналы автоматически. Журнал не коммитится и содержит сохраненные тексты; не удаляйте его при незавершенном сохранении.

## Свой репозиторий

Нажмите на название рабочей папки в верхней панели и укажите абсолютный путь к корню уже клонированного локального Git-репозитория. Поддерживается `~/`. Выбор сохраняется после перезапуска приложения. Кнопка «Исходная папка» возвращает рабочее пространство, заданное при запуске.

Подключенный репозиторий должен находиться вне кода specIDE и не использовать его Git-хранилище. Подключение само по себе не создает файлы требований, не меняет индекс и не делает коммитов. Новые требования сохраняются в `requirements/system/` выбранного репозитория. Существующие требования должны иметь совместимый frontmatter. Произвольные Markdown-файлы без него не конвертируются автоматически.

Выбранная папка общая для вкладок одного API. Переключение предупреждает о несохраненном тексте; сохранения из старой вкладки отклоняются до перезагрузки. Журналы и браузерные запросы восстановления изолированы по рабочим папкам. Клонирование по URL и авторизация пока не реализованы. Путь относится к машине, на которой работает API, а не к произвольному удаленному компьютеру.

## Создание требования

Кнопка с иконкой документа и плюсом открывает форму. Обязательное поле - название; ответственного можно не указывать. После подтверждения API создает файл `requirements/system/SR-NNN.md` со статусом `draft`, а интерфейс открывает его в редакторе. Отмена формы не создает файл.

Шаблон содержит назначение, поведение системы, правила и ограничения, обработку ошибок и критерии приемки. Он находится в `apps/api/src/system-template.ts`.

ID выдается API последовательно в рамках одного рабочего пространства с учетом занятых имен, идентификаторов и локального журнала операций. Повтор запроса с тем же ID операции не создает второй документ. При потере ответа форма сохраняет запрос в sessionStorage вкладки и позволяет проверить его результат, в том числе после перезагрузки страницы.

## Git

Кнопка Git открывает изменения и историю системных требований. Сравнение включает текст и frontmatter и строится по сохраненному файлу относительно HEAD. Новый файл показывается целиком, удаленный - как удаление. История показывает только версии, затрагивающие системные требования.

Для фиксации выбираются документы, просматривается их diff и вводится описание версии. Если файл, ветка или HEAD изменились после просмотра, запрос отклоняется до нового сравнения. Несохраненный текст редактора в Git не попадает. Подготовленные извне staged-изменения блокируют фиксацию и остаются нетронутыми.

Используется существующий Git-репозиторий рабочей папки, в том числе родительский для исходной демонстрационной папки. Можно подключить независимый репозиторий через верхнюю панель. Управляемый набор ограничен документами рабочего пространства с `type: system`; код приложения и BR/TC в него не входят. Имя репозитория и ветка видны в панели. Приложение автоматически не инициализирует репозиторий.

Нужен установленный Git и настроенные имя и email автора. Первая версия фиксации использует plumbing-команды: commit hooks и подписание коммитов не запускаются. Pull, управление ветками и PR/MR пока не поддерживаются. Подробности восстановления и временного индекса: [0003-git-workflow.md](docs/decisions/0003-git-workflow.md).

### Push

Кнопка Push в верхней части панели отправляет уже созданные коммиты. Направление показывается под вкладками: upstream текущей ветки, а при его отсутствии — `origin` и текущее имя ветки. Создание upstream автоматически не выполняется. Нужен один настроенный адрес отправки remote; detached HEAD и пустая история не поддерживаются.

Push отправляет всю историю ветки, включая коммиты не с требованиями. Перед отправкой это подтверждается отдельно. Незакоммиченные файлы и текст редактора не добавляются автоматически. Отправляется только подтвержденный коммит в одну ветку, без force, тегов и других веток. Если HEAD, ветка или адрес поменялись после просмотра, требуется повторное подтверждение. При расходящейся истории нужно получить и согласовать изменения вне приложения: автоматического pull/rebase нет.

Используются доступы Git/SSH машины, где запущен API. Ввод паролей и токенов через интерфейс не реализован. Сетевой вызов ограничен минутой; адреса с возможными секретами и вывод удаленных hooks не передаются в браузер. При потере подтверждения Push мог завершиться: его можно повторить после проверки направления, без переписывания удаленной истории. Автоматического повторения нет, отдельный журнал Push не ведется.

## Устройство

- `apps/web`: Next.js, React, MDXEditor, TanStack Query.
- `apps/api`: NestJS, файловые операции, очередь сохранений и журнал.
- `packages/schema`: общие схемы и контракты.
- `packages/markdown`: чтение и запись Markdown/frontmatter.
- `docs`: план MVP, отчет критика и архитектурные решения.

API доступен только через loopback. Один процесс API обслуживает одно активное рабочее пространство; несколько процессов с общей папкой состояния не поддерживаются. Записи и переключения из нескольких вкладок обрабатываются последовательно. Одновременная запись сторонней программой во время сохранения не поддерживается; завершившиеся внешние изменения обнаруживаются по версии файла.

## Текущие границы

Работают создание, навигация, поиск, редактор, свойства и сохранение. Невалидные документы диагностируются; неизвестные свойства frontmatter сохраняются. Неподдерживаемая редактором разметка блокирует сохранение.

Доступны Git status/diff/history, ручная фиксация выбранных требований и Push текущей ветки. Pull, управление ветками и AI еще не реализованы.

Архитектурные решения первого среза: [0001-first-slice.md](docs/decisions/0001-first-slice.md).

Создание документов: [0002-document-creation.md](docs/decisions/0002-document-creation.md).

Подключение независимого репозитория: [0004-workspace-connection.md](docs/decisions/0004-workspace-connection.md).
