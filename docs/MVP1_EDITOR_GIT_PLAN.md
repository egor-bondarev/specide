# specIDE MVP 1: продуктовый и инженерный план редактора + Git

Текущий фокус реализации: только системные требования (SR). Бизнес-требования и тест-кейсы остаются в доменной модели и дальнейшей дорожной карте, но пока отключены в UI и API сохранения; их демонстрационные файлы исключены из Git. Упоминания BR/TC ниже описывают расширение общего плана, а не обязательный объем текущего среза.

## 1. Цель и проверяемая гипотеза

Дать системному аналитику рабочее пространство, в котором он создает и редактирует требования визуально, сравнивает изменения и фиксирует версии в Git.

Гипотеза MVP: аналитик может пройти этот сценарий из интерфейса приложения без ручного написания Markdown и команд Git, а документы остаются читаемыми файлами, доступными вне приложения.

Основной пользователь первой версии - один системный аналитик, работающий с одним репозиторием требований. Совместная работа команды появится в следующих версиях.

## 2. Как работаем и принимаем решения

Каждый этап начинается с короткого описания пользовательской задачи и заканчивается демонстрацией рабочего сценария.

Для каждой функции фиксируем:

- какую задачу пользователя она решает;
- как пользователь проходит сценарий;
- какое поведение считаем успешным;
- какие ограничения допустимы в первой версии;
- что показала проверка на реальных примерах требований.

Владелец проекта участвует и в продуктовых, и в архитектурных решениях: определяет приоритеты, обсуждает границы компонентов, модель данных, интеграции и компромиссы реализации.

Перед существенным инженерным решением разбираем задачу, варианты, рекомендуемый подход и последствия для развития проекта. Принятое решение кратко фиксируем: контекст, выбор, причина и ограничения. Повседневные детали реализации не требуют отдельного согласования.

TypeScript остается языком реализации. Изучение его синтаксиса и учебные упражнения не являются целями проекта. Объяснения сосредоточены на устройстве системы, движении данных, надежности и причинах технических решений.

## 3. Границы MVP 1

### Обязательно для первой версии

- Открытие одного заранее подготовленного репозитория требований.
- Дерево документов и переход между ними.
- Создание бизнес-требования (BR), системного требования (SR) и тест-кейса (TC) из шаблонов.
- Визуальное редактирование текста с привычными кнопками форматирования.
- Редактирование карточки документа через форму: идентификатор, тип, название, статус и автор или ответственный.
- Сохранение документов в Markdown-файлы с их свойствами.
- Список новых и измененных документов.
- Сравнение изменений перед фиксацией версии.
- Создание Git-коммита с описанием и просмотр истории версий.
- Понятные состояния сохранения, выполнения операций и ошибок.

### Следующее расширение: MVP 1.5

- Подключение удаленного репозитория через интерфейс.
- Отправка и получение изменений: push и pull.
- Работа с ветками и отправка требований на ревью через PR/MR.
- Помощь при конфликтах изменений.

До этого расширения MVP 1 проверяет работу редактора и локальное версионирование. Он еще не закрывает командный процесс согласования требований в удаленном Git.

### Последующие версии

- Трассировка BR → SR → TC и анализ покрытия.
- AI-анализ требований и рекомендации по тестированию.
- Совместное редактирование, комментарии и разграничение доступа.
- Интеграции с внешними системами управления задачами и тестированием.

## 4. Основной пользовательский сценарий

1. Аналитик открывает рабочее пространство с репозиторием.
2. Находит существующий документ или создает новый из шаблона.
3. Заполняет свойства и редактирует содержание визуально.
4. Сохраняет документ и видит подтверждение сохранения.
5. Открывает список изменений и сравнивает документ с последней зафиксированной версией.
6. Выбирает документы для фиксации, добавляет описание и создает версию.
7. Видит новую запись в истории и может прочитать ее состав.

В интерфейсе различаем три состояния: изменения в редакторе, сохраненный файл и зафиксированная версия в Git. Сохранение текста само по себе не создает коммит. Отправка в удаленный репозиторий появится в MVP 1.5 как отдельное действие.

## 5. Архитектура и техническая основа

### Компоненты и ответственность

Базовый вариант для обсуждения перед реализацией:

| Компонент | Технологии | Ответственность |
| --- | --- | --- |
| Web | Next.js, React, TypeScript | Навигация, редактор, форма свойств, сравнение и история |
| API | NestJS, TypeScript | Операции с документами, проверка данных, управление рабочим пространством и Git |
| Общие пакеты | Схемы данных, обработка Markdown | Единые контракты документов, чтение и запись файлов |
| Рабочее пространство | Файловая система и Git CLI на стороне API | Файлы требований, изменения и история версий |

MDXEditor рассматриваем как первый кандидат для визуального редактирования. Перед выбором проверяем его на собственных документах: таблицах, блоках кода, ссылках и сохранении форматирования. TanStack Query используем для запросов и обновления данных интерфейса. Отдельное хранилище состояния добавляем при появлении потребности.

Для MVP предполагается локальный запуск web и API с одним подготовленным рабочим пространством. Путь к репозиторию задается на стороне API; браузер не получает произвольный доступ к файловой системе. Публичный доступ и несколько пользователей потребуют отдельного решения об авторизации и изоляции рабочих пространств.

Одно рабочее пространство обслуживает один процесс API. Несколько вкладок этого приложения допустимы: их изменения проходят через общую очередь операций. Одновременные записи сторонним редактором или Git-клиентом во время записи или фиксации приложения не поддерживаются в MVP. Последовательные внешние изменения обнаруживаем при следующем чтении или сохранении; обнаруженное расхождение не перезаписываем. Внутренняя блокировка API не является блокировкой произвольных внешних программ.

PostgreSQL и Prisma из общей концепции остаются кандидатами для будущих пользователей, настроек и поискового индекса. В первой версии необходимость базы проверяем отдельно: файлы и Git уже обеспечивают сохранение документов и версий. Индекс требований должен восстанавливаться из репозитория.

Redis, фоновые обработчики и AI-сервисы добавляются при появлении соответствующих задач.

### Структура приложения

```text
apps/
  web/                 интерфейс
  api/                 документы, рабочее пространство, Git
packages/
  schema/              схемы документов и контракты
  markdown/            чтение и запись Markdown с frontmatter
```

В API выделяем границы Workspace, Documents и Git. Documents отвечает за содержание и файлы; Git отвечает за версии и состояние репозитория. Сохранение документа не вызывает коммит автоматически.

### Хранение и модель документов

Для MVP предлагаем Markdown с согласованным набором форматирования и YAML frontmatter для свойств. Выполнение произвольных MDX-компонентов потребует отдельного решения и не нужно для базового сценария.

```text
requirements/
  business/BR-001.md
  system/SR-001.md
tests/
  test-cases/TC-001.md
```

Документ содержит стабильный идентификатор, тип, название, статус, ответственного и текст. Статусы: `draft`, `review`, `approved`, `deprecated`. Для типов сохраняем единый словарь: `business`, `system`, `test_case`.

Связи между документами предусматриваем в схеме как необязательное поле для дальнейшей трассировки. Граф связей и анализ покрытия остаются за рамками MVP 1. Точную схему, правила идентификаторов и поведение неизвестных полей утверждаем на примерах до реализации сохранения.

Git хранит зафиксированные версии; рабочие файлы - сохраненные изменения до коммита; редактор - еще не сохраненный текст. При записи свойства и содержание формируют один файл. Неподдерживаемая разметка и неизвестные свойства не должны молча исчезать.

### Поток данных и API

```text
Редактор и форма свойств
  -> запрос на сохранение
  -> проверка данных и версии документа
  -> запись Markdown-файла
  -> обновление списка изменений Git

Выбранные сохраненные документы + описание
  -> проверка снимка просмотренного сравнения
  -> создание коммита
  -> обновление статуса и истории
```

Предварительные контракты, которые уточняем перед реализацией соответствующего этапа:

| Операция | API |
| --- | --- |
| Информация о рабочем пространстве | `GET /workspace` |
| Список документов | `GET /documents` |
| Чтение и создание | `GET /documents/:id`, `POST /documents` |
| Сохранение | `PUT /documents/:id` |
| Изменения репозитория | `GET /git/status` |
| Сравнение документа | `GET /git/diff?path=...` |
| Фиксация выбранных файлов | `POST /git/commit` |
| История и состав версии | `GET /git/history`, `GET /git/commits/:hash` |
| Проверка результата изменяющей операции | `GET /operations/:operationId` |

Контракт сохранения включает версию прочитанного файла, например хеш содержимого. Проверка версии и запись выполняются в одной критической секции очереди рабочего пространства. Если два запроса прочитали одну версию, первый сохраняется, а второй получает конфликт. Атомарная замена файла защищает от частичной записи, но сама по себе не защищает от конкурирующего сохранения.

При обнаружении внешнего изменения API возвращает конфликт, а интерфейс сохраняет текст пользователя и предлагает перечитать документ. Ошибки валидации, отсутствующий файл и конфликт имеют различимые ответы. Граница гарантии для внешних программ указана выше в модели запуска.

Ответ сравнения включает токен снимка: базовый коммит (или отсутствие первого коммита), выбранные пути, состояния удаления и хеши показанного сохраненного содержания. Запрос коммита передает этот токен. До подготовки коммита внутри очереди проверяем совпадение базы и выбранного содержания со снимком. При расхождении ничего не фиксируем, показываем обновленное сравнение и требуем повторного подтверждения. В коммит передаем именно проверенное содержание; нельзя заново прочитать и незаметно подставить более свежие байты.

Изменяющие запросы получают `operationId`, создаваемый клиентом до отправки. Повтор с тем же ID и теми же параметрами возвращает известный результат либо состояние выполнения; тот же ID с другими параметрами отклоняется. Минимальный журнал операций сохраняется вне версионируемых документов и переживает перезапуск API. Он содержит намерение, исходную версию или базовый коммит и результат: новую версию файла либо хеш коммита.

Потеря ответа означает «результат пока неизвестен», а не доказанный отказ. Интерфейс сохраняет текст, проверяет операцию по ее ID и перечитывает состояние. После прерывания API сначала сверяет журнал с файлами, индексом и Git, затем сообщает результат. Пока результат не выяснен, повторное изменение не запускается вслепую. Журнал не считается транзакцией с файловой системой сам по себе: восстановление между записью и отметкой об успехе проверяется отдельно.

### Правила надежности документов и Git

- Проверяем входящие данные во время выполнения; общих типов между web и API недостаточно.
- Записываем файл атомарно, чтобы прерывание операции не оставило половину документа.
- Проверяем уникальность идентификаторов; переименование заголовка не меняет идентификатор.
- Обрабатываем только пути внутри разрешенного рабочего пространства, включая проверку символических ссылок.
- Git вызывается с отдельными аргументами без подстановки пользовательского текста в shell-команду.
- Для статуса используем структурированный машинный формат Git; для новых документов и репозитория без коммитов предусматриваем отдельное поведение сравнения.
- Все изменяющие операции приложения, включая создание, проверку версии с записью и фиксацию, выполняются последовательно для рабочего пространства. При коммите сверяем содержание и базу с подтвержденным пользователем снимком сравнения.
- Коммит включает только выбранные документы. Чужие staged-изменения не включаем и не сбрасываем; их наличие до начала операции является понятной причиной отказа.
- Собственные незавершенные операции отличаем от чужого индекса по журналу и проверяемому состоянию. После сбоя приложение должно восстановить свою операцию или безопасно отменить только собственную подготовку, сохранив рабочие файлы. Затем пользователь может повторить фиксацию из интерфейса.
- До реализации коммитов проверяем стратегию индекса на отдельном прототипе: обычный индекс с восстановлением либо изолированная подготовка. Критерии выбора - сохранность чужих staged-изменений, восстановление после прерывания и согласованность HEAD, рабочего индекса и файлов после успеха. Сам по себе временный индекс не доказывает выполнение последнего условия.
- Если состояние отличается от зафиксированного в журнале и принадлежность изменений неизвестна, автоматическую очистку не выполняем. Показываем диагностику и приостанавливаем изменяющие операции до разбора; это исключение для постороннего вмешательства, а не нормальный исход собственного сбоя.
- Сразу определяем автора коммита и поведение при отсутствии Git identity. Ошибка коммита не удаляет рабочие файлы.

## 6. Этапы реализации

### Этап 0. Согласование основы и первый технический каркас

**Результат:** зафиксированы границы MVP и архитектура, приложение запускается локально.

Инженерные задачи:

- Подготовить примеры BR, SR и TC и согласовать формат файлов.
- Выбрать структуру проекта, инструмент управления зависимостями и команды запуска.
- Создать web, API и общие пакеты; подключить проверку типов, форматирование и запуск проверок.
- Настроить одно рабочее пространство и отдельный демонстрационный репозиторий.
- Проверить обмен web и API и отобразить информацию об открытом проекте.
- На небольшом Git-прототипе проверить восстановление после прерывания подготовки и после создания коммита до ответа клиенту. Выбрать стратегию индекса и журнала по результату, до реализации этапа 5.

**Совместное решение:** подтвердить локальную модель запуска, границы web/API, необходимость базы и набор возможностей редактора для MVP.

**Критерий готовности:** проект воспроизводимо запускается по инструкции; web получает данные от API, а технические решения и ограничения записаны. Прототип подтверждает возможность восстановления Git-операции; иначе стратегию пересматриваем до основного Git-интерфейса.

### Этап 1. Рабочее пространство и навигация

**Пользовательский результат:** аналитик понимает, какой проект открыт и где находятся документы.

Объем:

- Рабочее пространство одного подготовленного репозитория.
- Дерево документов с разделами BR, SR и TC.
- Открытие документа и отображение его названия, типа и статуса.
- Состояния пустого проекта и ошибки открытия документа.

**Критерий готовности:** пользователь открывает несколько документов по очереди; выбранный документ и его содержание всегда соответствуют друг другу. Недоступный документ сопровождается понятным сообщением.

**Инженерные задачи:** реализовать чтение списка и документа, разбор frontmatter и проверку его структуры; добавить дерево и состояния загрузки. Невалидный файл показывать с диагностикой, остальные документы продолжать открывать. Предусмотреть репозиторий без документов и дубли идентификаторов.

### Этап 2. Визуальное редактирование и сохранение

**Пользовательский результат:** аналитик оформляет требование привычными редакторскими действиями и сохраняет его.

Объем:

- Заголовки, жирный и курсивный текст, списки, ссылки, таблицы и блоки кода.
- Отмена и повтор изменений.
- Явное действие сохранения и индикатор несохраненных изменений.
- Предупреждение о несохраненном тексте при переходе к другому документу.

**Критерий готовности:** после сохранения и повторного открытия документа текст и поддерживаемое форматирование сохраняются. Ошибка сохранения не отображается как успех и не очищает внесенный текст.

Если два сохранения пришли с одной исходной версией, успешно применяется только одно; второе получает конфликт без потери текста во вкладке. При потере ответа интерфейс выясняет результат сохранения по `operationId`, а не создает повторную запись с новым ID.

Поддержку изображений и других вложений уточняем на примерах документов до начала этого этапа. Если без них нельзя проверить основной сценарий, добавляем минимально необходимый вариант и явно корректируем объем MVP.

**Инженерные задачи:** проверить и подключить редактор; реализовать преобразование файла в свойства и текст и обратно, API сохранения и отслеживание несохраненных правок. Добавить защиту от перезаписи внешних изменений и атомарную запись.

**Проверка:** набор документов проходит цикл «открыть → изменить → сохранить → открыть» без потери поддерживаемого содержания. Отдельно проверить ошибку записи, внешнее изменение файла и неподдерживаемую разметку. Форматирование файла должно быть стабильным, чтобы сохранение не создавало лишний Git diff.

Дополнительно проверить одновременные запросы из двух вкладок, потерю ответа после успешной записи и перезапуск API между записью файла и регистрацией результата в журнале.

### Этап 3. Создание документов и их свойства

**Пользовательский результат:** аналитик создает BR, SR или TC, не подготавливая файл вручную.

Объем:

- Три базовых шаблона с согласованными разделами.
- Форма свойств документа.
- Уникальный идентификатор в рамках проекта.
- Статусы: черновик, на проверке, согласовано, устарело.
- Проверка обязательных полей и понятные сообщения об ошибках.

**Критерий готовности:** пользователь создает документ каждого типа; документ появляется в нужном разделе, открывается и сохраняется вместе со своими свойствами. Повторный идентификатор не допускается. Изменение названия сохраняет идентификатор.

Статус в MVP - свойство документа. Назначение статуса «согласовано» пока не запускает процесс согласования и не подтверждает прохождение ревью.

**Инженерные задачи:** добавить схемы проверки свойств, шаблоны, правила выдачи ID и размещения файла; реализовать создание через API и форму. Не перезаписывать существующий файл при совпадении имени или идентификатора.

### Этап 4. Просмотр и сравнение изменений

**Пользовательский результат:** аналитик понимает, что именно войдет в новую версию.

Объем:

- Список новых и измененных документов, а также удалений, если они произошли вне приложения.
- Сравнение сохраненного содержания с последней зафиксированной версией.
- Отображение изменений текста и свойств документа.
- Для нового документа - просмотр всего добавляемого содержания.
- Выбор документов для фиксации.

**Критерий готовности:** пользователь видит конкретные добавления и удаления. Несохраненные изменения редактора обозначены отдельно. Вне выбранного набора документы не попадают в коммит.

Просмотренное сравнение связано со снимком содержания и базового коммита. Если выбранный файл изменился или HEAD сдвинулся после просмотра, прежнее подтверждение больше не действует. До нового просмотра фиксация отклоняется; это также работает для нового и удаленного документа.

**Инженерные задачи:** реализовать Git status, diff и модель списка изменений; определить базой сравнения последний коммит, а не только staged-содержимое. Отобразить изменения свойств и текста, новые и удаленные файлы. Выбор набора для коммита хранить отдельно от состояния редактора.

### Этап 5. Фиксация версии и история

**Пользовательский результат:** аналитик сохраняет осмысленный набор изменений в истории проекта.

Объем:

- Фиксация выбранных документов с обязательным описанием.
- Подтверждение успешной операции или понятная причина ошибки.
- Состояние «результат пока неизвестен» при потере ответа с последующей проверкой операции по ID.
- История с автором, датой и описанием версии.
- Просмотр списка документов, вошедших в выбранную версию.

**Критерий готовности:** новая версия появляется в истории, выбранные изменения исчезают из списка незафиксированных, остальные остаются. Повторное открытие приложения сохраняет историю. При ошибке фиксации работа пользователя остается доступной.

Собственное прерывание после подготовки индекса не заставляет пользователя исправлять Git вручную: приложение восстанавливает операцию или безопасно отменяет свою подготовку и позволяет повтор. Если коммит создан, но ответ потерян, проверка возвращает его хеш, не создавая вторую версию. Совпадение содержания коммита с подтвержденным снимком проверяется отдельно от состава файлов.

**Инженерные задачи:** реализовать проверку выбранного набора, создание коммита, чтение истории и состава версии. Настроить автора, обработку отсутствия изменений и обновление интерфейса после операции. Для MVP история загружается ограниченными порциями.

**Проверка:** использовать отдельные временные Git-репозитории: первый коммит, несколько измененных файлов с выбором части, удаление, непустой индекс, отсутствие автора и ошибка операции. Убедиться, что невыбранные изменения остаются в рабочем пространстве и не попадают в коммит.

Добавить прерывание после подготовки индекса, прерывание после создания коммита до записи результата, потерю ответа, повтор с тем же `operationId` и изменение выбранного файла или HEAD после просмотра diff. Проверить возможность продолжения после перезапуска, отсутствие дублирующего коммита и сохранность чужого индекса.

### Этап 6. Проверка MVP на реальной задаче аналитика

**Пользовательский результат:** полный сценарий можно использовать для подготовки требования.

Объем:

- Небольшой набор примеров BR, SR и TC из одной предметной области.
- Проверка основного сценария от создания до записи в истории.
- Проверка сохранности документов после закрытия и повторного открытия приложения.
- Проверка файлов обычными средствами вне приложения.
- Исправление проблем, мешающих завершить сценарий.

**Критерий готовности:** аналитик проходит сценарий без подсказок по Markdown и командам Git. Полученные файлы читаются вне приложения, а созданные версии видны в обычной истории Git.

**Инженерные задачи:** проверить сквозной сценарий в браузере; проверить ошибки открытия, сохранения и фиксации; подготовить инструкцию запуска и демонстрационный набор. Убедиться, что пользователь видит состояния ожидания и не может случайно запустить повторную фиксацию.

**Проверки качества:** модульные проверки схем и чтения/записи документов, интеграционные проверки файловых и Git-операций, один основной браузерный сценарий от создания до истории. Добавлять их по мере реализации соответствующего этапа.

## 7. Как проверяем ценность

Во время пробного использования записываем наблюдения:

| Что проверяем | На что смотрим |
| --- | --- |
| Удобство создания | Может ли пользователь создать документ без помощи |
| Достаточность редактора | Хватает ли форматирования для выбранных примеров требований |
| Понятность сохранения | Различает ли пользователь сохранение текста и фиксацию версии |
| Понятность сравнения | Может ли пользователь объяснить, что изменилось перед коммитом |
| Надежность | Сохранились ли содержание, свойства и форматирование после повторного открытия |
| Польза истории | Может ли пользователь найти нужную версию и понять состав изменений |

Первая проверка возможна на собственных требованиях. Затем полезно дать сценарий другому аналитику и записать, где понадобились пояснения. Целевые значения времени выполнения задач задаем после первого прогона.

## 8. Условия готовности MVP 1

- Полностью работает основной сценарий из раздела 4.
- Доступны три типа документов и согласованные шаблоны.
- Пользователь понимает, сохранен ли текст и зафиксирована ли версия.
- Содержание и свойства документов сохраняются после повторного открытия.
- Сравнение и коммит отражают выбранный набор изменений.
- История доступна из интерфейса и через обычный Git.
- При проверке нет нерешенных ошибок, ведущих к потере текста или ложному подтверждению сохранения.
- Ограничения первой версии известны по результатам пробного использования.
- Проверки документов, файловых операций и Git подтверждают сохранность данных и правильный состав коммитов.
- Проверки подтверждают соответствие коммита просмотренному снимку, конфликт перекрывающихся сохранений и восстановление собственных прерванных операций без ручной очистки Git.
- Потеря ответа API не приводит к слепому повтору записи или коммита; результат можно выяснить после переподключения и перезапуска API.
- Есть инструкция запуска, а ключевые архитектурные решения и принятые ограничения зафиксированы.

## 9. Точки совместного принятия инженерных решений

| Когда | Что обсуждаем | Что фиксируем |
| --- | --- | --- |
| До начала реализации | Границы MVP, локальный запуск, компоненты, база данных | Схему системы и ответственность компонентов |
| До реализации документов | Markdown или MDX, frontmatter, ID, неизвестные поля | Формат файлов и примеры |
| До интеграции редактора | Варианты редактора, поддерживаемая разметка, вложения | Результат проверки на примерах и ограничения |
| До сохранения | Явное или автоматическое сохранение, очередь записей, границы внешнего доступа | Состояния документа, проверку версии, ID операции и поведение при конфликте |
| До коммитов | Подтвержденный снимок, индекс, авторство, журнал и восстановление | Результаты прототипа, правила операций и проверки частичных отказов |
| Перед расширением на удаленный Git | Провайдер, доступ, ветки, PR/MR и конфликты | Отдельный план MVP 1.5 |

На обсуждение выносим конкретные варианты с рекомендацией и последствиями. Решения принимаем до зависимой реализации; детали кода и исправления в рамках выбранного подхода выполняются без отдельного согласования.

## 10. Ближайший шаг

Выбрать одну предметную область и подготовить по одному примеру BR, SR и TC. По ним согласовать состав карточки, содержание шаблонов и необходимое форматирование. Затем подтвердить архитектуру этапа 0 и реализовать первый сценарий: открыть документ, отредактировать, сохранить и открыть повторно.
