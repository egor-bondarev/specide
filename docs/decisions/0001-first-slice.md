# 0001. Первый рабочий срез specIDE

Статус: первоначальная реализация на основе согласованного плана; решения можно пересмотреть вместе до расширения MVP.

## Границы

Первый срез позволяет открывать существующие требования, редактировать содержание и свойства, сохранять их в файлы. Git-операции не выполняются. Прототип Git-индекса из этапа 0 остается отдельной незавершенной задачей; весь этап 0 не считается закрытым.

Текущий продуктовый фокус - системные требования. В API и UI активен только тип `system`; модели `business` и `test_case` остаются в общей схеме. Их примеры исключены из рабочего дерева и Git через `.gitignore`. Ссылки на удаленные демонстрационные BR/TC убраны из SR-примера. При будущей Git-интеграции набор управляемых документов также должен ограничиваться активным типом; автоматического удаления чужих файлов в подключенных репозиториях нет.

## Компоненты

Next.js отвечает за интерфейс, NestJS - за файловые операции. Общие пакеты содержат схемы и обработку Markdown. Это сохраняет обсужденные границы и позволяет подключить Git на стороне API. Цена отдельного API - два процесса локального запуска; для пользователя они запускаются одной командой.

MDXEditor выбран как первый проверяемый кандидат. Редактор работает только в браузере. Используем Markdown, таблицы, списки, ссылки, цитаты и блоки кода; выполнение MDX-компонентов не поддерживается.

Базы данных, очереди фоновых задач и отдельного state manager нет: их роль в этом срезе не обоснована.

## Данные

Одно требование - один Markdown-файл с YAML frontmatter. ID стабилен; тип и ID при сохранении не меняются. Название, статус и ответственный редактируются через форму.

Схема допускает неизвестные поля, включая связи и приоритет. При изменении тела исходное оформление frontmatter сохраняется. При изменении свойств YAML сериализуется заново, неизвестные значения сохраняются, но комментарии и оформление YAML могут измениться. Проверяем семантическую сохранность; побайтовое совпадение обещаем только для сохранения без изменений.

## Сохранение и восстановление

Версия файла - SHA-256 всего исходного содержания. Проверка версии и запись проходят через общую очередь в одном API-процессе. Запись выполняется через временный файл и rename.

До изменения файла сохраняется журнал с ID операции, отпечатком запроса и исходным/ожидаемым хешами. После успешной записи журнал содержит результат. При перезапуске незавершенная операция сверяется с файлом: ожидаемый хеш означает успех, исходный - отсутствие записи, третий вариант требует разбора и не перезаписывается автоматически.

Это гарантия для остановки процесса, а не обещание полной устойчивости к потере питания. Файловая запись и журнал не являются общей транзакцией. Незавершенные временные файлы игнорируются сканером.

UI сохраняет незавершенный запрос в sessionStorage текущей вкладки. При потере ответа или перезагрузке проверяет его по ID. Повтор с тем же ID не применяет изменение заново; ID с другим запросом отклоняется.

Поддерживается один API-процесс на рабочее пространство. Внешние программы не участвуют в очереди: одновременно редактировать файлы ими во время сохранения приложения нельзя. Отдельную межпроцессную блокировку и совместное редактирование рассматриваем до расширения модели запуска.

## Что нужно проверить до Git-интеграции

- Снимок просмотренного diff должен соответствовать содержанию коммита.
- Собственный сбой подготовки индекса не должен требовать ручной очистки Git.
- Потеря ответа не должна создавать дублирующий коммит.
- Чужие staged-изменения должны оставаться неприкосновенными.
