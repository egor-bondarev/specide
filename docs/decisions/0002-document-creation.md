# 0002. Создание системных требований

## Сценарий и контракт

В интерфейсе доступна одна форма: название обязательно, ответственный необязателен. Тип всегда `system`, начальный статус `draft`. ID и путь определяет сервер. Запрос `POST /documents` принимает `operationId`, `title`, `owner`; произвольные поля вроде `id` и `type` отклоняются.

После успеха документ появляется в дереве и открывается в редакторе. Отмена формы не вызывает API создания. При несохраненных правках текущего документа переход к созданию требует подтверждения; отмена самой формы сохраняет исходный черновик.

Шаблон хранится отдельно в `apps/api/src/system-template.ts`, чтобы его можно было обсуждать и изменять независимо от файловых операций.

## Идентификаторы и запись

Используется существующая очередь рабочего пространства: выдача ID, журналирование и публикация файла выполняются последовательно. Новый номер следует за максимальным найденным в именах файлов, валидных метаданных (включая дубли) и локальном журнале. Большие числовые ID обрабатываются через BigInt. Зарегистрированные локальные номера повторно не выдаются; глобальную уникальность между независимыми клонами будем решать при командной Git-интеграции.

Файл создается в `requirements/system`. Папки назначения не могут быть символическими ссылками. Публикация подготовленного временного файла выполняется через hard link в той же папке: существующий целевой файл не перезаписывается. После публикации временное имя удаляется. Сохранение существующего документа по-прежнему использует атомарную замену через rename.

## Повторы и восстановление

Создание использует тот же журнал операций, что и сохранение. Записи имеют вид `create` или `save`; старые записи без вида трактуются как `save`. Для создания исходная версия равна `null`, то есть файла еще нет.

После прерывания ожидаемый хеш файла означает успех, отсутствие файла означает невыполненное создание, другое содержание или ошибка чтения требуют разбора. Самопроизвольного повторного создания с новым ID при неизвестном исходе нет.

UI сохраняет незавершенный запрос до отправки. При потере ответа или перезагрузке форма проверяет `GET /operations/:id`. Если запрос не успел зарегистрироваться, он повторяется с тем же ID и данными. Тот же ID с другим содержанием отклоняется. Журнал и файл не являются общей транзакцией; границы прерывания проверяются отдельно.

## Ограничения

Сохраняется модель одного API-процесса на рабочее пространство. Создание файла не выполняет staging, коммит или отправку в удаленный Git. BR и TC остаются в модели и отключены для пользовательских операций.
